# Do_Bi · AI 小说写作工具 · 项目规划与技术方案

> 版本：**v2.0（按功能取舍清单重写）**
> 形态：Web 自托管　|　AI：**全部通过 API 接入**（不含本地模型）
> 本次变更：新增第 3 章「功能取舍清单」，据此重排架构、数据、流水线、里程碑与 WBS；许可证处理不在本次决策范围内

## 1. 项目概览

### 1.1 一句话定位

**一个「写得出、不崩、可干预」的长篇小说创作工具**——人和 AI 共用同一条创作流水线，既能陪写，也能全自动跑完整本。

### 1.2 目标用户

| 用户 | 核心诉求 | 对应能力 |
|---|---|---|
| 网文作者 | 快速产出初稿、稳定更新、不崩设定 | 真相文件 · 审计深度 · 反 AIGC |
| 个人创作者 / 爱好者 | 有想法但写不动，需要陪练 | 共创对话 · 实时干预 · 伏笔可视化 |
| 工作室 / 小团队 | 批量生产、流程可控 | 整本生产流程 · 滚动规划 · 断点恢复 |

### 1.3 核心价值主张

现有工具两极分化：**重表单型**（填十几个字段才有产出）和**一键傻瓜型**（前 5 章惊艳，第 10 章开始人设崩塌、伏笔遗忘、无限水文）。Do_Bi 站在中间：

- **Chat-first**：从一句话灵感开始，不填表
- **强一致**：结构化真相文件承载长期记忆，跨几十万字不漂移
- **双模式**：同一套引擎支持「人机协同」与「全自动」，可随时切换
- **可举证**：每条审计结论都能引用原文，不给你"感觉不对"的模糊反馈

### 1.4 非目标（明确不做）

- ❌ 本地模型推理 / Ollama / Electron 桌面端（全部走 API 接入）
- ❌ 交互式分支游戏（Play 模式）、同人番外模式
- ❌ 市场趋势雷达、封面图像生成、多语言翻译出版、EPUB/PDF 出版级导出
- ❌ 多人实时协作编辑
- ❌ 自训练 / 微调模型

## 2. 设计原则

1. **模型只负责叙述，应用负责记住真相**
   LLM 输出是「提议」，由应用裁决是否写入正史。
2. **一套流水线，两种干预策略**
   全自动与人机协同是同一条流水线上「干预策略」的不同取值。
3. **先确定性，后智能**
   能用规则零成本判定的问题（去 AI 味、称呼不一致）不用 LLM。
4. **真相落盘为纯文本 + 结构化双形态**
   机器可校验（JSON/SQLite），人可读可改（Markdown/YAML），可 Git 版本化。
5. **审计必须可举证**
   任何审计结论都要带原文证据，否则不可执行、不可申诉。
6. **可中断、可续跑**
   长篇生产必然跨天跨周，任何一步都必须能精确恢复。

### 3.2 逐项落地要点

**① 真相文件 / 长期记忆（InkOS）**
落成 Do_Bi 的 9 个真相文件（见 §5.1）。核心设计取舍：**采用 InkOS 的"7 文件 + 资源账本"骨架，并补 2 个文件**——`style_profile.json`（承接文风仿写）与 `outline_graph.json`（承接章纲依赖图）。存储采用**双形态**：schema 校验的 JSON 为准，Markdown 投影供人读；另建 SQLite 做时序记忆与相关性检索。所有写入走 Proposal → Validate → Commit。

**② 审计深度（InkOS）**
**不做一上来 33 维。** 分级落地：
- **L1 确定性规则**（P0，零 LLM 成本）：13 条，含 InkOS 的禁用句式 / 连续"了"字 / 套话密度 / 词汇疲劳 / 视角跳跃，加我们自有的不可变特征违背、伏笔超期
- **L2 LLM 维度审计**（P0 起 5 维 → P1 扩到 15 维）：OOC、设定冲突、伏笔遗漏、时间线矛盾、文风偏移；P1 增补战力/等级漂移、信息泄露、节奏单调、支线停滞、情感弧线断裂、场景重复、对话同质化、因果断裂、动机不足、爽点缺失
- 严重度三级：`blocker / major / minor`，决定是否阻塞定稿

**③ 反 AIGC / 去 AI 味（InkOS）**
- **P0**：L1 规则内的"去 AI 味"部分——禁止句式、套话密度、连续虚词、段落长度均匀度、词汇疲劳。**全部零成本、可确定性判定**
- **P2**：扩展为完整管线——**外部 AIGC 检测器接入 + 反检测改写**。检测器设计为可插拔（GPTZero 类 API 或本地启发式），改写走"定点修复"而非整段重写

**④ 文风仿写（InkOS）**
分析参考小说样本，产出 `style_profile.json`（句长分布、高频句式、叙述人称与视角、描写/对话比例、用词偏好、禁忌表达）。写入后作为**必选上下文**注入 Writer Prompt（确定性选择，不参与检索竞争），同时也作为 L2「文风偏移」审计的对照基准。

**⑤ MCP 扩展（InkOS）**
以 **MCP 客户端**身份接入外部工具服务器，让「查设定」「查资料」「查历史章节」等动作可以走外部工具而不是硬编码。设计为**可插拔、可关闭**：MCP 不可用时全流程必须照常运行（降级为内置检索）。适用场景：外部设定库、百科、用户自建的知识服务。

**⑥ 滚动规划（ainovel-cli）**
完整移植其三层结构：
- **罗盘 Compass**：终局方向 + 活跃长线 + 规模估计，每个卷边界刷新
- **骨架弧**：只记 `目标 + 预估章数`，写到该弧才展开详细章纲
- **渐进细化**：展开时参考前文摘要、角色快照、风格规则
- 初始只规划前 2 卷，后续按需生成

**⑦ 断点恢复（ainovel-cli）**
移植其 **step 级**粒度，恢复点为 `plan / draft / audit / revise / commit`。附恢复场景表：规划中断→补全缺失项；章节写作中断→读草稿续写；审计中断→重跑审计；修订队列未清空→继续处理；弧展开中断→检测骨架弧并触发展开。幂等靠 `idempotency_key`。

**⑧ 质量评审可举证（ainovel-cli）**
**评审结论必须引用原文**，禁止"感觉不通顺"这类无法执行的反馈。评审维度首批 7 项：设定一致性、角色行为、节奏、叙事连贯、伏笔、钩子、审美品质（细分描写质感 / 叙事手法 / 对话区分度 / 用词质量 / 情感打动力）。每条输出 `{维度, 严重度, 原文证据, 修改建议}`。

**⑨ 实时干预（ainovel-cli）**
用户可在**不暂停生产**的前提下注入修改意见。系统需自动完成两件事：**评估影响范围**（影响当前章 / 后续大纲 / 已定稿章）、**按范围重写**。影响已定稿章节时，生成"追溯修订提案"交人工确认，不静默改写历史。

**⑩ 伏笔可视化（MuMuAINovel）**
- **P0 必须有数据支撑**：`pending_hooks.jsonl` 带 `status / planted_chapter / resolved_chapter / importance / suggested_resolve_by`
- **P2 前端**：伏笔时间线 + 状态泳道（待回收 / 已回收 / 超期告警）+ **未回收告警**，并统计**伏笔回收率**（作为核心质量指标）

**⑪ 章纲依赖图 / 思维链（MuMuAINovel）**
- **P1 数据**：`outline_graph.json` 记录章节节点与有向依赖边（`depends_on` 表示"本章的哪些内容依赖第 N 章的哪条线"），并保留每章生成的思维链摘要（为什么这样安排）
- **P2 前端**：依赖图可视化 + 节点展开看思维链，用于排查"第 40 章埋的因，第 12 章没接上"这类结构问题

**⑫ 拆书（MuMuAINovel）**
导入已有小说 → 反推结构：切分章节、抽取角色与关系、抽取世界观规则、抽取伏笔线索与回收点、生成 `style_profile.json`。产出为**可编辑的提案**而非直接写入（复用 Proposal → Validate → Commit）。用途：同题材仿写、旧作续写、竞品结构分析。

**⑬ 整本生产流程（AI-Novel-Writing-Assistant）**
不采纳其内部模块实现，只采纳**"从一句灵感走到完整小说"的端到端编排形态**：把 Architect → 滚动规划 → Writer → Auditor → Reviser → Archivist 串成一条可无人值守跑完全本的流水线，并支持中途暂停、人工接管、断点续跑。这是 §7 编排层 P1 的目标形态。

## 4. 系统架构

```
┌──────────────────────────────────────────────────────────────┐
│ ① 交互层  工作台 · 共创对话 · 伏笔看板 · 章纲依赖图 · 审计报告 │
├──────────────────────────────────────────────────────────────┤
│ ② 干预策略层  手动逐步 / 半自动确认 / 全自动 + 实时干预 Steer  │
├──────────────────────────────────────────────────────────────┤
│ ③ 编排层  Coordinator → Architect·Writer·Auditor·Reviser      │
│            └ 滚动规划（罗盘 / 骨架弧 / 渐进细化）              │
├──────────────────────────────────────────────────────────────┤
│ ④ 上下文组装  Token 预算 · BM25 检索 · 关联章节推荐 · 文风注入 │
├──────────────────────────────────────────────────────────────┤
│ ⑤ 一致性引擎  审计（L1 规则 / L2 多维 / 可举证评审）           │
│                + 反 AIGC 去味管线 + 文风仿写                   │
├──────────────────────────────────────────────────────────────┤
│ ⑥ 项目状态层  9 个真相文件 · SQLite 时序记忆 · 检查点快照       │
└──────────────────────────────────────────────────────────────┘
        ↓                                          ↓
  ⑦ 模型适配层（OpenAI 兼容 API）        ⑧ MCP 客户端（可关闭）
```

| 层 | 职责 | 关键约束 |
|---|---|---|
| ① 交互层 | 编辑、确认、可视化 | 只调后端 API，不直连模型 |
| ② 干预策略层 | 决定各环节自动 / 确认 / 手动；承接实时干预 | 运行中可随时切换；影响历史时须人工确认 |
| ③ 编排层 | 调度 Agent、滚动规划、状态机、断点恢复 | 同书串行，避免状态竞争 |
| ④ 上下文组装 | 预算内挑最相关信息 | 文风为确定性必选，不参与检索竞争 |
| ⑤ 一致性引擎 | 发现问题 + 可举证 + 定点修复 | L1 确定性优先；审计必须带原文证据 |
| ⑥ 项目状态层 | 存储真相与历史 | 双形态落盘；写入必经 Validate |
| ⑦ 模型适配层 | 统一所有厂商调用 | 只依赖 OpenAI 兼容协议 |
| ⑧ MCP 客户端 | 接入外部工具服务器 | **可关闭**，不可用时全流程降级运行 |

## 5. 数据层设计

### 5.1 项目目录结构（9 个真相文件）

```
projects/<project-id>/
├─ meta.json                  # 元信息：题材、篇幅、模式、预算
├─ world.md                   # 世界观规则（不可违反的硬设定）
├─ characters.jsonl           # 角色矩阵
├─ current_state.md           # 世界当前状态快照
├─ pending_hooks.jsonl        # 伏笔池            ← 支撑「伏笔可视化」
├─ chapter_summaries.jsonl    # 章节摘要（累积）
├─ subplot_board.md           # 支线进度板
├─ outline_graph.json         # 章纲依赖图 + 思维链 ← 支撑「章纲依赖图」
├─ style_profile.json         # 文风档案          ← 支撑「文风仿写」
├─ outline.json               # 分卷/分章大纲（滚动规划产物）
├─ chapters/ch_0001.md        # 正文
├─ audits/ch_0001.json        # 审计报告（含原文证据）
├─ reviews/ch_0001.json       # 可举证质量评审
├─ checkpoints/               # step 级执行快照
├─ memory.db                  # SQLite 时序记忆（相关性检索）
└─ state/*.json               # 真相文件的机器可校验镜像
```

> 与 v1.0 相比：新增 `outline_graph.json`、`style_profile.json`、`reviews/`、`memory.db`、`state/`，共 9 个真相文件（原 7 个 + 文风 + 章纲图）。

### 5.2 关键数据结构

**characters.jsonl** —— 区分「不可变特征」与「可变状态」，这是防崩核心

```json
{
  "id": "char_001", "name": "沈砚", "role": "protagonist",
  "immutable_traits": ["左眉骨有旧疤", "不饮酒", "惯用左手"],
  "personality": "沉默寡言，重承诺",
  "speech_style": "短句，很少用感叹词",
  "relationships": [{"target": "char_002", "type": "师徒", "note": "心存愧疚"}],
  "state": {"location": "北境·雁回关", "status": "受伤", "known_secrets": ["文脉真相"]},
  "first_appearance": 1, "updated_at_chapter": 17
}
```

**pending_hooks.jsonl** —— 伏笔必须能统计回收率（支撑伏笔可视化）

```json
{
  "id": "hook_007",
  "content": "沈砚幼年见到的青铜灯并未熄灭",
  "planted_chapter": 4, "status": "planted", "resolved_chapter": null,
  "importance": "major", "linked_characters": ["char_001"],
  "suggested_resolve_by": 40
}
```
`status` ∈ `planted / resolved / abandoned`，另在前端派生 `overdue`（`planted` 且超过 `suggested_resolve_by`）。

**outline_graph.json** —— 支撑章纲依赖图与思维链

```json
{
  "nodes": [
    {"chapter": 17, "title": "雪落雁回", "arc": "雁回关篇",
     "goal": "识破周崇通敌，埋下铜灯线索",
     "beats": ["雪夜巡查", "发现靴印", "放走旧友", "铜灯初亮"],
     "rationale": "此处放走旧友，是为第 24 章其反水做动机铺垫，避免届时动机不足"},
    {"chapter": 24, "title": "旧友刀锋", "arc": "雁回关篇", "goal": "旧友反水", "beats": ["…"]}
  ],
  "edges": [
    {"from": 24, "to": 17, "type": "motivation", "note": "第 24 章反水依赖第 17 章的放走行为"},
    {"from": 24, "to": 4,  "type": "setup",      "note": "铜灯来源追溯到第 4 章"}
  ]
}
```
`edges.type` ∈ `motivation / setup / payoff / causality / parallel`。`rationale` 即"思维链"的可读摘要。

**style_profile.json** —— 文风仿写产物，也是文风审计的对照基准

```json
{
  "source": "参考样本《XXX》前 8 章",
  "sentence_length": {"mean": 21.4, "p90": 46},
  "narrative": {"person": "第三人称限知", "tense": "过去", "pov_switch": "rare"},
  "ratio": {"description": 0.46, "dialogue": 0.31, "action": 0.23},
  "preferred_patterns": ["短句收尾成段", "环境描写承托情绪"],
  "banned_expressions": ["不由自主地", "心中一凛", "空气仿佛凝固"],
  "lexicon": {"语气词": "极少", "四字格": "克制"}
}
```

**audits/ch_XXXX.json** / **reviews/ch_XXXX.json** —— 审计必须带原文证据

```json
{
  "chapter": 17,
  "l1_violations": [{"rule": "词汇疲劳", "hit": "仿佛", "count": 6, "threshold": 3}],
  "items": [
    {"dim": "设定冲突", "severity": "major", "fixed": false,
     "evidence": "「灯没有点，可灯芯那一小截，是亮的」",
     "suggestion": "与 world.md「铜灯须以血引方燃」冲突，建议改为割破指尖后自行亮起",
     "ref": "ch_0017.md#para-5"},
    {"dim": "伏笔遗漏", "severity": "minor", "fixed": false,
     "evidence": "hook_005「不该有的车辙」已超过建议回收章（16）",
     "suggestion": "可在本章雪夜场景补一笔车辙呼应", "ref": "pending_hooks.jsonl#hook_005"}
  ]
}
```

**checkpoints/** —— 断点恢复依据

每次 step 成功后写 `checkpoints/ch_0017_step3_audit.json`，含 `chapter`、`step`（plan/draft/audit/revise/commit）、`status`、`attempt`、`idempotency_key`、`output_ref`、`timestamp`。

### 5.3 写入规则（关键）

所有对真相文件的写入必经 **Proposal → Validate → Commit**：

1. Agent 产出「提案」（新增事实 / 修改角色状态 / 新增伏笔 / 调整大纲）
2. 校验器检查：字段合法性、与 `immutable_traits` 是否冲突、与 `world.md` 是否矛盾、伏笔是否重复
3. 通过才落盘；冲突降级为「待人工确认项」，**不自动写入**

## 6. AI 模型接入方案

> 全部通过 API 调用，无本地模型。目标：**换厂商不改业务代码、成本可控、失败可恢复**。

### 6.1 统一适配层

只依赖 **OpenAI 兼容协议**，用官方 `openai` SDK 通过 `base_url` + `api_key` 切换厂商。

| 字段 | 说明 |
|---|---|
| `name` | 展示名，如 `DeepSeek` |
| `base_url` | 兼容端点 |
| `api_key_ref` | 指向环境变量的键名，**不落明文** |
| `models` | 可用模型（含 `context_window`、`supports_json`、`supports_stream`） |
| `priority` | 主/备顺序，用于降级链 |

需处理的厂商差异：`max_tokens` vs `max_completion_tokens` 命名；`response_format` / `json_schema` 支持度不一 → **能力探测 + 自动降级**；部分厂商不支持并行 tool calls → 串行降级。

### 6.2 模型角色分工（随本次取舍扩充）

| 环节 | 模型档位 | 温度 | 输出格式 |
|---|---|---|---|
| 世界观/大纲（Architect） | 高能力 | 0.75 | JSON |
| 章纲 + 依赖图与思维链 | 高能力 | 0.60 | JSON |
| 正文（Writer，注入文风） | 高能力 + 长上下文 | 0.92 | 流式文本 |
| **审计 L2（多维度）** | 中能力（便宜） | 0.15 | JSON |
| **可举证评审（7 维）** | 中高能力 | 0.30 | JSON（含原文引用） |
| **反 AIGC 改写** | 高能力 | 0.40 | JSON Patch |
| **文风仿写分析** | 中高能力 | 0.20 | JSON |
| **拆书（导入反推）** | 中高能力 | 0.30 | JSON |
| 摘要 / 事实抽取（Archivist） | 便宜 | 0.10 | JSON |
| 对话式共创 | 中高能力 | 0.70 | JSON + 文本 |

约束：**同环节主备模型必须都支持所需能力**（如 JSON 模式），否则降级链会中途断掉。

### 6.3 密钥与配置管理

- API Key **只存环境变量 / 服务端密钥库**，前端永不接触
- 设置页只展示「已配置 / 未配置」，提交密钥走一次性加密传输
- 多租户时密钥按用户隔离存储
- 日志与错误信息对 Key 脱敏

### 6.4 调用链与流式

```
前端 SSE ──► FastAPI 编排器 ──► 适配层 ──► Provider API
                  │
                  └─► 逐块转发（生成中可中断 / 可停止）
```
- 正文生成走 **SSE 流式**，支持「停止」立即中止并保存半成品
- 结构化任务（大纲 / 审计 / 评审）非流式，等完整 JSON
- 下游步骤输入**必须来自落盘数据**，不依赖内存对话历史（保证断点可续）

### 6.5 成本与预算控制（四道闸门）

1. **每章 Token 预算上限**：超出则裁剪低优先级上下文，不报错
2. **上下文分层预算**（默认）：

   | 用途 | 占比 | 说明 |
   |---|---|---|
   | 系统规则 / 提示词 | 5% | |
   | 角色卡 + 世界观 | 15% | |
   | 动态事实表 | 10% | |
   | 历史摘要 | 20% | |
   | 当前草稿 | 30% | |
   | 输出预留 | 20% | |
   | **文风档案** | **确定性必选** | 体量小，不占配额、不参与检索竞争 |

3. **调用计量**：记录 `model / step / prompt_tokens / completion_tokens / cost / latency`，按项目 / 章 / 天聚合
4. **预算熔断**：达阈值提示，超额暂停并挂起 checkpoint，**不静默烧钱**

> 注意：本次新增的审计维度扩展、反 AIGC 管线、可举证评审都会增加调用量，**熔断是必需品而非可选项**。

### 6.6 稳定性设计

| 问题 | 对策 |
|---|---|
| 超时 | 连接与读取超时分开配置，长文本给足读取超时 |
| 429 / 5xx | 指数退避重试，上限 3 次，加抖动 |
| 4xx 参数错误 | **不重试**，记录并降级或报错 |
| 输出非法 JSON | 解析容错（提取代码块 → 修复尾逗号 → 再失败则带错误重试一次） |
| 主力模型不可用 | 降级链：主力 → 备用 → 挂起 checkpoint 并提示 |
| 重试导致重复写入 | 每 step 带 `idempotency_key`，写入前查重 |
| 并发写同一本书 | 项目级锁串行；不同项目可并行 |
| **MCP 服务不可用** | 自动降级为内置检索，**不阻塞主流程** |
| 上下文超窗 | 按 §6.5 预算裁剪；不支持长上下文时自动切摘要模式 |

### 6.7 可观测性

- **调用日志**：请求元信息 + 响应摘要（提示词全文可选开关，用于复盘调优）
- **审计报告**：每章 `audits/ch_XXXX.json`，含问题列表、严重度、**原文证据**、是否已修复
- **核心质量指标**：**伏笔回收率** · L1 违规数 · L2 审计通过率 · 每章平均成本 · 修订轮次
- 前端可见「本章花了多少 Token / 多少钱」

### 6.8 检索方案

**P0 不上向量库**，用 BM25（SQLite FTS5 或 `rank_bm25`）做设定卡、事实表、历史摘要检索。理由：数据量小、零额外依赖、离线可用、短文本效果好。`memory.db` 承载时序记忆；向量后端做**可插拔接口预留**，后续按需替换。

### 6.9 MCP 扩展（本次采纳）

- 以 **MCP 客户端**接入外部工具服务器（stdio / HTTP 传输）
- 暴露给 Agent 的工具示例：`lookup_setting`（外部设定库）、`search_reference`（资料检索）、`fetch_history`（外部章节存档）
- **强制降级**：MCP 未配置或连接失败时，全部工具调用回落到内置实现
- 设置页提供 MCP 服务器列表与连通性测试

## 7. Agent 流水线设计

### 7.1 角色职责

| Agent | 输入 | 输出 | 说明 |
|---|---|---|---|
| **Coordinator** | 用户意图、项目状态 | 调度决策 | 只做编排与仲裁，不生成内容 |
| **Architect** | 灵感 / 对话记录 | `world.md`、`characters.jsonl`、`outline.json`、`outline_graph.json` | 建立创作宪法 |
| **Writer** | 章纲 + 上下文 + 文风档案 | 章节正文（流式） | 唯一产出正文的角色 |
| **Auditor** | 正文 + 真相文件 | `audits/*.json`（L1 + L2，含证据） | |
| **Reviewer** | 正文 + 章纲 + 依赖图 | `reviews/*.json`（7 维，含原文引用） | **新增，可举证评审** |
| **Reviser** | 正文 + 审计报告 | JSON Patch 补丁 | 定点修复，最小改动 |
| **Archivist** | 定稿正文 | 摘要、事实抽取、伏笔更新、依赖边更新 | 沉淀为可检索资产 |

### 7.2 单章执行时序

```
章纲 ─► 上下文组装 ─► 草稿 ─► 审计(L1+L2) ─► 可举证评审 ─► 去 AI 味 ─► 修订 ─► 定稿 ─► 更新真相
 ▲            │            │              │             │          │            │
 └──── 干预策略层插入「确认点」；实时干预可在任意时刻注入 ─────┴──────────┘
```

每环节结束写 checkpoint。干预策略决定哪些环节需人工确认：

- **全自动**：全部 auto（审计发现问题自动进修订；冲突项标记后继续）
- **半自动**：章纲、审计报告两个节点确认
- **手动逐步**：每个环节都停下等待确认

### 7.3 滚动规划（本次采纳）

不一次性规划全部章节（大纲到 300 章必然空心化）：

- **罗盘**：终局方向 + 活跃长线 + 规模估计，每卷结束刷新
- **骨架弧**：每卷只记 `目标 + 预计章数`，写到该卷才展开成详细章纲
- **渐进细化**：展开时参考前文摘要、角色快照、文风规则
- **初始只规划前 2 卷**

### 7.4 断点恢复（本次采纳）

- 恢复粒度：`plan / draft / audit / revise / commit`
- 恢复时读最后一个成功 checkpoint，重放后续步骤
- 幂等：同 `idempotency_key` 的写入只生效一次
- **恢复场景表**

  | 中断时机 | 恢复行为 |
  |---|---|
  | 规划阶段 | 检查已保存设定，自动补全缺失项 |
  | 某章写作中（有草稿未提交） | 读已有草稿继续 |
  | 审计进行中 | 重新触发审计 |
  | 修订队列未清空 | 继续处理待修订项 |
  | 弧/卷展开中断 | 检测骨架弧，自动触发 Architect 展开 |

- 目标：kill -9 或断网后重启，精确续跑，不重复不丢稿

### 7.5 实时干预 Steer（本次采纳）

不暂停生产，用户随时注入意见。系统必须自动完成：

1. **意图解析**：把自然语言意见转为结构化指令（如"节奏太慢，压缩到三段"→ `{target: ch_18, action: compress, scope: 3}`
2. **影响范围评估**：当前章 / 后续大纲 / 已定稿章
3. **按范围执行**：仅影响当前章 → 直接重写；影响后续大纲 → 更新 `outline_graph.json` 并提示；**影响已定稿章 → 生成追溯修订提案，等人工确认**

### 7.6 整本生产流程（本次采纳）

P1 的目标形态：一个 `run` 指令从灵感跑到完成，期间无需人工。约束：

- 支持 `stop_conditions`：出现 blocker 级未决问题、预算超限、连续 N 章审计不通过 → 自动暂停
- 支持中途切人工：随时把模式改为 `confirm`，在下个确认点停下
- 全程可断点续跑
- 结束产出：正文全稿 + 审计与评审报告 + 伏笔回收率 + 成本清单

## 8. 一致性引擎

### 8.1 L1 确定性规则（P0，零 LLM 成本）

13 条，用正则与规则判定：

1. 称呼 / 姓名不一致
2. 角色已标记「死亡 / 离场」却再次出场
3. `immutable_traits` 被违背
4. 禁用句式命中（来自 `style_profile.banned_expressions`）
5. 套话密度超阈值
6. 连续「了」「的」字句
7. 词汇疲劳（同一词 / 短语在章内出现次数超阈值）
8. 段落长度异常（超长或全篇等长）
9. 视角切换未标注
10. 时间线倒错
11. 伏笔超期未回收
12. 数值 / 等级设定前后矛盾
13. 描写 / 对话 / 动作比例偏离文风档案

### 8.2 L2 LLM 维度审计（分级扩展）

**P0 首批 5 维**：OOC · 设定冲突 · 伏笔遗漏 · 时间线矛盾 · 文风偏移

**P1 扩展至 15 维**：增补战力/等级漂移 · 信息泄露 · 节奏单调 · 支线停滞 · 情感弧线断裂 · 场景重复 · 对话同质化 · 因果断裂 · 动机不足 · 爽点缺失

> 「审计深度」的价值在维度覆盖，但**每维都是一次成本**。因此 P0 只做 5 维，P1 再扩，并允许项目级开关（关掉不关心的维度省钱）。

### 8.3 可举证质量评审（P1，本次采纳）

与 L2 审计的区别：审计对**设定与逻辑**，评审对**写作质量**。7 维：

设定一致性 · 角色行为 · 节奏 · 叙事连贯 · 伏笔 · 钩子 · 审美品质（细分：描写质感 / 叙事手法 / 对话区分度 / 用词质量 / 情感打动力）

**硬要求：每维必须引用原文举证。** 输出格式固定为 `{维度, 严重度, 原文证据, 修改建议}`；无证据的结论直接丢弃，不进入报告。这条约束的意义是——**让反馈可执行、可申诉**，而不是给作者一堆无法落地的形容词。

### 8.4 反 AIGC / 去 AI 味（分级落地）

- **P0（确定性层）**：走 L1 规则 —— 禁用句式、套话密度、连续虚词、段落长度均匀度、词汇疲劳；命中即触发 **spot-fix 定点修复**（只改违规句，不整段重写）
- **P2（完整管线）**：
  1. **检测**：可插拔检测器（外部 AIGC 检测 API 或本地启发式打分）
  2. **定位**：把检测结果映射到具体段落 / 句子
  3. **改写**：定点修复，改后**重跑 L1** 确认没引入新问题
  4. 循环上限 2 轮，超限标记交人工（防死循环烧钱）

### 8.5 文风仿写（P2，本次采纳）

1. **分析**：读参考样本（可整本或前 N 章），产出 `style_profile.json`
2. **注入**：作为**确定性必选上下文**进入每次 Writer 调用（不参与检索竞争，保证每章文风一致）
3. **校验**：作为 L2「文风偏移」审计与 L1 第 13 条的对照基准
4. **可覆盖**：用户可手工编辑档案（如删掉某条"禁用表达"）

### 8.6 修订策略

- `blocker` / `major` → **定点修复**，输出 JSON Patch（`replace / insert / delete`），前端可预览 diff
- `minor` → 只记录，不自动改
- 自动修订后**必须重跑 L1**，L1 通过才算闭环完成
- 单章修订循环上限 2 轮，超限挂起交人工

## 9. 干预策略层

**「人机协同」与「全自动」统一的关键，也是实时干预的落点。**

```json
{
  "mode": "semi-auto",
  "steps": {
    "plan": "confirm", "draft": "auto", "audit": "confirm",
    "review": "auto", "deai": "auto", "revise": "auto", "commit": "confirm"
  },
  "stop_conditions": [
    "audit.blocker_exists", "budget.exceeded",
    "audit.fail_streak >= 3", "steer.affects_committed"
  ]
}
```

- 每 step 取值 `auto` / `confirm` / `manual`
- 运行中可随时切换：全自动跑到一半想接管，切 `confirm` 即在下个确认点停下
- `stop_conditions` 是**全自动模式的安全阀**：不失控烧钱、不产出崩溃内容
- **实时干预**独立于 mode：任何模式下都可注入，但影响已定稿章时强制转人工确认

### 10.2 设计方向（Design Contract 已在原型阶段冻结）

## 12. 里程碑（按采纳能力重排）

### P0 · 一致性内核

**形态**：FastAPI 纯后端 + CLI，**不含 UI**。

**交付物**
- 项目骨架 + OpenAI 兼容适配层（Provider 配置、重试、降级、计量）
- **真相文件 9 件套** + Proposal → Validate → Commit（能力①）
- 上下文组装：Token 预算 + BM25 + 关联章节推荐 + 文风必选注入
- Architect / Writer / Auditor 三条最小链路
- **审计 L1 13 条确定性规则**（能力②③）
- **审计 L2 首批 5 维**（能力②）
- **step 级 checkpoint 与恢复**（能力⑦）
- `pending_hooks` 数据层完整（能力⑩ 的数据部分）
- CLI：`novel new / plan / write <n> / audit / resume`

**验收标准**
1. 一条命令从一句灵感生成 **10 章**正文
2. **伏笔回收率可统计**（埋了 N 条、回收 M 条）
3. **L1 违规为零**（角色状态不漂移、不可变特征无违背）
4. **中断可续**：kill 进程后重启，精确续跑，不重复不丢稿
5. 每章 Token 与成本可查

### P1 · 双模式全自动流水线

- **滚动规划**（罗盘 / 骨架弧 / 渐进细化）（能力⑥）
- **整本生产流程**：`run` 指令跑到完成或熔断（能力⑬）
- **可举证质量评审 7 维**（能力⑧）
- **审计扩展至 15 维**，含项目级维度开关（能力②）
- **实时干预 API 层**：意图解析 + 影响范围评估（能力⑨）
- **章纲依赖图数据层**：`outline_graph.json` 节点与边（能力⑪ 数据）
- 干预策略层三模式 + `stop_conditions` 熔断

**验收**
1. 全自动模式无人值守写完 **20 章**，中途可切人工接管
2. 所有审计与评审结论 **100% 带原文证据**
3. 卷边界能自动展开下一卷骨架弧，大纲不空心化
4. 断点恢复在 5 类中断场景下均验证通过

### P2 · 人机协同工作台

- 按 Design Contract 实现前端（复用批次一原型）
- 页面：工作台 · 共创 · 角色 · **伏笔看板** · **章纲与依赖图** · **审计报告** · **文风档案** · 设置
- **反 AIGC 完整管线**：检测 → 定位 → 改写 → 重跑 L1（能力③）
- **文风仿写**：样本分析 + 档案注入 + 可编辑（能力④）
- **实时干预 UI** + diff 预览 + 证据跳转
- SSE 流式 + 干预开关 + 成本显示

**验收**：浏览器内完成「立项 → 逐章确认 → 定稿」全流程，且能通过依赖图与伏笔看板定位结构问题。

### P3 · 扩展能力

- **拆书**：导入反推结构 + 提案审查（能力⑫）
- **MCP 扩展**：外部工具服务器接入 + 连通性测试 + 降级验证（能力⑤）
- 备选：节奏模板库、关系图谱可视化、提示词工坊

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **范围爆炸**（最大风险） | 永远发不了版 | 13 项能力已按里程碑分配；P0 严格限定为「后端内核 + CLI」，可视化全在 P2 |
| **审计成本失控** | Token 费用翻倍 | P0 只做 5 维 + L1 确定性规则；P1 扩展维度但**允许项目级开关**；预算熔断强制开启 |
| **反 AIGC 改写死循环** | 烧钱且质量下降 | 改写后重跑 L1；循环上限 2 轮；超限交人工 |
| **实时干预影响面失控** | 静默改写历史章节 | 影响已定稿章时**强制转人工确认**，不自动改写 |
| **依赖图变成摆设** | 只存不用 | `outline_graph.json` 必须**被上下文组装真实消费**（`motivation` 边反查前章），否则不进入 P1 |
| **文风档案注入过度** | 文风僵化、千篇一律 | 档案只约束"特征区间"（句长分布、比例），不锁死具体句式；用户可编辑 |
| **全自动质量天花板** | 产出不可用 | `stop_conditions` 熔断；不追求 100% 自动 |
| **模型输出格式不稳** | 流程中断 | JSON 解析容错 + 能力探测降级 + 带错误重试 |
| **MCP 依赖不可用** | 主流程阻塞 | **强制降级为内置检索**，MCP 永远是增强而非依赖 |
| **长上下文失控** | 成本与质量双降 | 摘要压缩 + 检索取用，不靠"全塞 prompt" |
| **厂商锁定** | 议价权与可用性风险 | 只依赖 OpenAI 兼容协议，Provider 可配置可替换 |
| **密钥泄露** | 安全事故 | 密钥仅服务端、日志脱敏、前端永不接触 |

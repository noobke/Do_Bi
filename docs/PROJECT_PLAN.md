# Do_Bi · AI 小说写作工具 · 项目规划与技术方案

> 版本：v1.0（规划稿，待评审）
> 形态：Web 自托管　|　AI：**全部通过 API 接入**（不含本地模型）　|　许可证：GPL-3.0

---

## 1. 项目概览

### 1.1 一句话定位

**一个「写得出、不崩、可干预」的长篇小说创作工具**——人和 AI 共用同一条创作流水线，既能陪写，也能全自动跑完整本。

### 1.2 目标用户

| 用户 | 核心诉求 | 对应能力 |
|---|---|---|
| 网文作者 | 快速产出初稿、稳定更新、不崩设定 | 一致性引擎 + 全自动模式 |
| 个人创作者 / 爱好者 | 有想法但写不动，需要陪练 | 对话式共创 + 逐章确认 |
| 工作室 / 小团队 | 批量生产、提示词可复用 | 提示词工坊 + 多项目并行 |

### 1.3 核心价值主张

现有工具两极分化：**重表单型**（填十几个字段才有产出）和**一键傻瓜型**（前 5 章惊艳，第 10 章开始人设崩塌、伏笔遗忘、无限水文）。Do_Bi 站在中间：

- **Chat-first**：从一句话灵感开始，不填表
- **强一致**：结构化的「真相文件」承载长期记忆，跨几十万字不漂移
- **双模式**：同一套引擎支持「人机协同」与「全自动」，随时切换
- **可控可查**：每个环节可确认、可回滚，审计报告可读

### 1.4 非目标（明确不做）

- ❌ 本地模型推理 / Ollama 集成（后续如有需要，走 OpenAI 兼容 API 统一接入）
- ❌ 多人实时协作编辑
- ❌ 平台发布、排版出版、封面生成
- ❌ 自训练 / 微调模型

## 2. 设计原则

1. **模型只负责叙述，应用负责记住真相**
   LLM 输出是「提议」，由应用裁决是否写入正史。防止「模型幻觉一个设定就变成了事实」。
2. **一套流水线，两种干预策略**
   全自动与人机协同不是两套系统，而是同一条流水线上「干预策略」的不同取值。
3. **先确定性，后智能**
   能用规则零成本判定的问题（去 AI 味、称呼不一致）不用 LLM；LLM 审计只做规则做不到的事。
4. **真相落盘为纯文本**
   Markdown / YAML / JSONL，天然支持 Git 版本控制与人工直接编辑。
5. **审计—修订闭环**
   没有审计的生成等于没有质量控制；每个产出物都必须过审。

## 3. 系统架构

```
┌──────────────────────────────────────────────────────────┐
│  ① 交互层  Web 工作台 / 对话式共创 / 图谱与伏笔看板        │
├──────────────────────────────────────────────────────────┤
│  ② 干预策略层  ★ 手动逐步 / 半自动确认 / 全自动            │
├──────────────────────────────────────────────────────────┤
│  ③ 编排层  Coordinator → Architect·Writer·Auditor·Reviser │
├──────────────────────────────────────────────────────────┤
│  ④ 上下文组装  Token 预算 · 检索 · 关联章节推荐            │
├──────────────────────────────────────────────────────────┤
│  ⑤ 一致性引擎  确定性规则审计 + LLM 维度审计 + 修订闭环    │
├──────────────────────────────────────────────────────────┤
│  ⑥ 项目状态层  真相文件（唯一真相源）· 检查点快照          │
└──────────────────────────────────────────────────────────┘
                          ↓
              ⑦ 模型适配层（OpenAI 兼容 API）
```

| 层 | 职责 | 关键约束 |
|---|---|---|
| ① 交互层 | 编辑、确认、可视化 | 只调用后端 API，不直连模型 |
| ② 干预策略层 | 决定每个环节「自动 / 确认 / 手动」 | 策略可全局配置，也可单环节覆盖 |
| ③ 编排层 | 调度 Agent、管理状态机、断点恢复 | 同一本书串行执行，避免状态竞争 |
| ④ 上下文组装 | 在 Token 预算内挑最相关的信息 | 预算可配，超限先降级而非报错 |
| ⑤ 一致性引擎 | 发现问题 + 定点修复 | L1 确定性优先，L2 才用 LLM |
| ⑥ 项目状态层 | 存储真相与历史 | 纯文本 + 可 Git；写入需经校验 |
| ⑦ 模型适配层 | 统一所有厂商调用 | 只依赖 OpenAI 兼容协议 |

## 4. 数据层设计

### 4.1 项目目录结构

```
projects/<project-id>/
├─ meta.json                 # 元信息：题材、篇幅、文风、模式、预算
├─ world.md                  # 世界观规则（不可违反的硬设定）
├─ characters.jsonl          # 角色矩阵
├─ current_state.md          # 世界当前状态快照
├─ pending_hooks.jsonl       # 伏笔池
├─ chapter_summaries.jsonl   # 章节摘要（累积）
├─ subplot_board.md          # 支线进度板
├─ style_profile.json        # 文风档案
├─ outline.json              # 分卷/分章大纲
├─ chapters/ch_0001.md       # 正文
├─ audits/ch_0001.json       # 审计报告
└─ checkpoints/              # 执行快照（step 级）
```

### 4.2 关键数据结构

**characters.jsonl** —— 区分「不可变特征」与「可变状态」，这是防崩的核心

```json
{
  "id": "char_001",
  "name": "沈砚",
  "role": "protagonist",
  "immutable_traits": ["左眉骨有旧疤", "不饮酒", "惯用左手"],
  "personality": "沉默寡言，重承诺",
  "speech_style": "短句，很少用感叹词",
  "relationships": [{"target": "char_002", "type": "师徒", "note": "心存愧疚"}],
  "state": {"location": "北境·雁回关", "status": "受伤", "known_secrets": ["文脉真相"]},
  "first_appearance": 1,
  "updated_at_chapter": 17
}
```

**pending_hooks.jsonl** —— 伏笔必须能统计回收率

```json
{
  "id": "hook_007",
  "content": "沈砚幼年见到的青铜灯并未熄灭",
  "planted_chapter": 4,
  "status": "planted",
  "resolved_chapter": null,
  "importance": "major",
  "linked_characters": ["char_001"],
  "suggested_resolve_by": 40
}
```

`status` ∈ `planted` / `resolved` / `abandoned`。审计时 `status=planted` 且超过 `suggested_resolve_by` 即告警。

**chapter_summaries.jsonl**

```json
{
  "chapter": 17,
  "title": "雪落雁回",
  "summary": "沈砚识破副将通敌，却在雪夜放走了旧友，青铜灯第一次亮起。",
  "key_events": ["识破副将", "放走旧友", "青铜灯亮起"],
  "characters_present": ["char_001", "char_004"],
  "hooks_planted": ["hook_012"],
  "hooks_resolved": ["hook_007"],
  "state_changes": ["沈砚受伤", "雁回关戒严"]
}
```

**checkpoints/** —— 断点恢复的依据

每次 step 成功后写入 `checkpoints/ch_0017_step3_audit.json`，内容含：`chapter`、`step`（plan/draft/audit/revise/commit）、`status`、`attempt`、`idempotency_key`、`output_ref`、`timestamp`。恢复时从最后一个成功 checkpoint 之后继续。

### 4.3 写入规则（关键）

所有对真相文件的写入必须经过 **Proposal → Validate → Commit** 三步：

1. Agent 产出「提案」（如新增 3 条事实、修改角色状态）
2. 校验器检查：字段合法性、与 `immutable_traits` 是否冲突、是否与 `world.md` 矛盾
3. 通过才落盘。冲突则降级为「待人工确认项」，不自动写入

## 5. AI 模型接入方案（核心）

> 全部通过 API 调用，无本地模型。这一层的目标是：**换厂商不改业务代码、成本可控、失败可恢复**。

### 5.1 统一适配层

只依赖 **OpenAI 兼容协议**，用官方 `openai` SDK 通过 `base_url` + `api_key` 切换厂商：

```python
# 概念示意
client = AsyncOpenAI(base_url=provider.base_url, api_key=provider.api_key)
```

**Provider 配置模型**

| 字段 | 说明 |
|---|---|
| `name` | 展示名，如 `DeepSeek` |
| `base_url` | 兼容端点 |
| `api_key_ref` | 指向环境变量的键名，**不落明文** |
| `models` | 该 Provider 可用模型列表（含 `context_window`、`supports_json`、`supports_stream`） |
| `priority` | 主/备顺序，用于降级链 |

适配器需处理厂商差异：
- `max_tokens` vs `max_completion_tokens` 命名差异
- `response_format` / `json_schema` 支持度不一 → **能力探测 + 自动降级**（不支持则改用「提示词约束 + 解析容错」）
- 部分厂商不支持并行 tool calls → 串行降级

接入厂商（示例，均可通过配置增删）：OpenAI、Anthropic、Google Gemini、DeepSeek、通义千问、Kimi、智谱、硅基流动等任何 OpenAI 兼容端点。

### 5.2 模型角色分工

不同环节用不同档位的模型，是成本与质量的关键杠杆：

| 环节 | 模型档位 | 温度 | 输出格式 | 可缓存的确定性调用 |
|---|---|---|---|---|
| 世界观/大纲（Architect） | 高能力 | 0.7–0.8 | JSON | 否 |
| 章纲（Chapter Plan） | 高能力 | 0.6 | JSON | 否 |
| 正文（Writer） | 高能力 + 长上下文 | 0.85–0.95 | 流式文本 | 否 |
| 审计（Auditor L2） | 中能力（便宜） | 0.1–0.2 | JSON | 部分 |
| 修订（Reviser） | 高能力 | 0.3–0.5 | JSON Patch | 否 |
| 摘要/事实抽取 | 便宜模型 | 0.1 | JSON | 否 |
| 对话式共创 | 中高能力 | 0.6–0.8 | JSON + 文本 | 否 |

约束：**同一环节的主备模型必须都支持所需能力**（如 JSON 模式），否则降级链会在中途断掉。

### 5.3 密钥与配置管理

- API Key **只存环境变量 / 服务端密钥库**，前端永不接触
- 前端设置页只展示「已配置 / 未配置」与 Provider 列表，提交密钥走一次性加密传输
- 支持多租户（自托管多用户）时，密钥按用户隔离存储
- 所有日志与错误信息对 Key 做脱敏

### 5.4 调用链与流式

```
前端 SSE ──► FastAPI 编排器 ──► 适配层 ──► Provider API
                  │
                  └─► 逐块转发（生成中可中断 / 可停止）
```

- 正文生成走 **SSE 流式**，前端逐字呈现，支持「停止」立即中止并保存半成品
- 结构化任务（大纲/审计）走非流式，等待完整 JSON
- 所有下游步骤的输入必须来自落盘数据，**不依赖内存中的对话历史**（保证断点可续）

### 5.5 成本与预算控制

四道闸门：

1. **每章 Token 预算上限**：超出则截断低优先级上下文（而非报错）
2. **上下文分层预算**（默认值，可配）：

   | 用途 | 占比 |
   |---|---|
   | 系统规则 / 提示词 | 5% |
   | 角色卡 + 世界观 | 15% |
   | 动态事实表 | 10% |
   | 历史摘要 | 20% |
   | 当前草稿 | 30% |
   | 输出预留 | 20% |

3. **调用计量**：每次调用记录 `model / step / prompt_tokens / completion_tokens / cost / latency`，落库；按项目 / 按章 / 按天聚合
4. **预算熔断**：项目可设总预算，达阈值提示、超额则暂停并挂起 checkpoint（不静默烧钱）

另：非实时任务（摘要、事实抽取）可合并成一次批量调用，降低调用次数。

### 5.6 稳定性设计

| 问题 | 对策 |
|---|---|
| 超时 | 连接超时与读取超时分开配置，长文本生成给足读取超时 |
| 429 / 5xx | 指数退避重试，上限 3 次，加抖动 |
| 4xx 参数错误 | **不重试**，直接记录并降级或报错 |
| 输出非合法 JSON | 解析容错（提取代码块 → 修复尾逗号 → 再失败则重试一次，带上错误信息） |
| 主力模型不可用 | 降级链：主力 → 备用 → 挂起 checkpoint 并提示 |
| 重试导致重复写入 | 每个 step 带 `idempotency_key`，写入前查重 |
| 并发写同一本书 | 同一项目串行执行（项目级锁）；不同项目可并行 |
| 上下文超窗 | 按 §5.5 预算裁剪；模型不支持长上下文时自动切摘要模式 |

### 5.7 可观测性

- **调用日志**：完整记录请求元信息与响应摘要（提示词全文可选开关，用于复盘调优）
- **审计报告**：每章一份 `audits/ch_XXXX.json`，含问题列表、严重度、是否已修复
- **质量指标**：伏笔回收率、L1 规则违规数、审计通过率、每章平均成本
- 前端提供「本章花了多少 Token / 多少钱」的可见性（对成本敏感的用户很重要）

### 5.8 检索方案

**P0 不上向量库**，用 BM25（SQLite FTS5 或 `rank_bm25`）对设定卡、事实表、历史摘要做检索。理由：数据量小、零额外依赖、离线可用、效果在设定卡这种短文本上够用。

后续若检索质量不达标，再引入 embedding + 向量库作为可插拔后端（接口预留）。

| 方法 | 路径 | 说明 |
|---|---|---|

| GET | `/api/projects` | 项目列表 |
| POST | `/api/projects/{id}/chat` | 对话式共创（多轮，输出结构化设定） |
| POST | `/api/projects/{id}/plan` | 生成/刷新世界观、角色、大纲 |
| POST | `/api/projects/{id}/chapters/{n}/plan` | 生成第 n 章章纲 |

## 6. Agent 流水线设计

### 6.1 角色职责

| Agent | 输入 | 输出 | 说明 |
|---|---|---|---|
| **Coordinator** | 用户意图、当前项目状态 | 调度决策 | 只做编排与仲裁，不生成内容 |
| **Architect** | 灵感 / 对话记录 | `world.md`、`characters.jsonl`、`outline.json` | 建立创作宪法 |
| **Writer** | 章纲 + 组装好的上下文 | 章节正文（流式） | 唯一产出正文的角色 |
| **Auditor** | 正文 + 真相文件 | 审计报告 JSON | L1 规则 + L2 LLM 维度 |
| **Reviser** | 正文 + 审计报告 | JSON Patch 补丁 | 定点修复，最小改动 |
| **Archivist** | 定稿正文 | 摘要、事实抽取、伏笔更新 | 沉淀为可检索资产 |

### 6.2 单章执行时序

```
章纲 ──► 上下文组装 ──► 草稿 ──► 审计(L1+L2) ──► 修订 ──► 定稿 ──► 更新真相
  ▲                        │              │                    │
  └──────── 干预策略层在此插入「确认点」 ───┴────────────────────┘
```

每个环节结束后写 checkpoint。`干预策略`决定哪些环节需要人工确认：

- **全自动**：全部 auto（审计发现问题自动进修订；冲突项标记后继续，不阻塞）
- **半自动**：章纲、审计报告两个节点确认
- **手动逐步**：每个环节都停下等确认

### 6.3 长篇规划：滚动视界

不一次性规划全部章节（大纲到 300 章必然空心化）：

- **罗盘**：终局方向 + 活跃长线 + 规模预估，每个「卷」结束时刷新
- **骨架弧**：每卷只记 `目标 + 预计章数`，写到该卷时才展开成详细章纲
- **渐进细化**：每次展开都参考前文摘要、角色快照、文风规则，越往后越准

### 6.4 断点恢复

- 恢复粒度：`plan / draft / audit / revise / commit`
- 恢复时读最后一个成功 checkpoint，重放后续步骤
- 幂等保证：同 `idempotency_key` 的写入只生效一次
- 目标：kill -9 或断网后重启，能精确续跑，不重复不丢稿

## 7. 一致性引擎

### 7.1 L1 确定性规则（零 LLM 成本，先做）

约 10 条，用正则与规则判定，绝对可靠：

1. 称呼/姓名不一致（同一角色多种写法）
2. 角色已标记「死亡/离场」却再次出场
3. `immutable_traits` 被违背（如「不饮酒」的角色饮酒）
4. 禁用句式 / 口头禅式套话密度超阈值
5. 连续「了」「的」字句
6. 段落长度异常（超长或全篇等长）
7. 视角切换未标注
8. 时间线倒错（同章内时间倒退且无标记）
9. 伏笔超期未回收（超过 `suggested_resolve_by`）
10. 数值/等级设定前后矛盾（修为、年龄、距离等抽取后比对）

### 7.2 L2 LLM 维度审计（首批只做 5 维）

不要一上来做 33 维。首批：

1. **OOC**（角色出戏）
2. **设定冲突**（与 `world.md` 矛盾）
3. **伏笔遗漏**（该回收未回收）
4. **时间线矛盾**
5. **文风偏移**（与 `style_profile.json` 不符）

每维输出 `{维度, 严重度, 证据, 建议}`。严重度 `blocker / major / minor`。

### 7.3 修订策略

- `blocker` / `major` → **定点修复**：Reviser 输出 JSON Patch（`replace / insert / delete`），前端可预览 diff
- `minor` → 只记录，不自动改
- 自动修订后**必须重跑 L1**（防止修订引入新问题），L1 通过才算闭环完成
- 单章修订循环上限 2 轮，超限挂起交人工（防止死循环烧 Token）

## 8. 干预策略层

**这是「人机协同」与「全自动」统一的关键。**

```json
{
  "mode": "semi-auto",
  "steps": {
    "plan":      "confirm",
    "draft":     "auto",
    "audit":     "confirm",
    "revise":    "auto",
    "commit":    "confirm"
  },
  "stop_conditions": ["audit.blocker_exists", "budget.exceeded"]
}
```

- 每个 step 取值 `auto` / `confirm` / `manual`
- 运行中可随时切换：全自动跑到一半想接管，切 `confirm` 即在下个确认点停下
- `stop_conditions` 定义强制中断条件，保证全自动模式不会失控烧钱或产出崩溃内容

## 9. Web 前端设计

### 9.1 信息架构与页面清单

| # | 页面 | 职责 | 关键组件 |
|---|---|---|---|
| 1 | 首页 / 项目列表 | 进入项目、看进度 | 项目卡、进度环、新建入口 |
| 2 | 共创对话 | Chat-first 立项，AI 多轮追问沉淀设定 | 对话流、设定卡实时预览 |
| 3 | **写作工作台**（核心） | 写作 + 确认 + 干预 | 三栏：目录树 / 编辑器 / 助手面板；干预开关 |
| 4 | 角色卡与关系图谱 | 管理角色与关系 | 角色卡、力导向关系图 |
| 5 | 伏笔看板 | 追踪伏笔，未回收告警 | 时间线、状态泳道 |

| 8 | 设置 | Provider / 模型 / 预算 | Provider 列表、模型映射、成本统计 |

导航（冻结）：`工作台 · 共创 · 角色 · 伏笔 · 大纲 · 审计 · 设置`

### 9.2 设计方向（Design Contract 将在原型阶段冻结）

- **Style tier**：`minimal-light` + **literary / editorial（文学编辑风）**
  理由：写作工具的气质应该是「纸与墨」，而非通用 SaaS 蓝紫渐变
- **气质关键词**：安静、克制、高可读性、编辑级排版
- **字体方向**（避免 Inter/Roboto 等 AI 味默认字体）：
  - 显示字体：衬线（中文思源宋体 `Noto Serif SC`，西文一款有个性的衬线）
  - 正文/UI：思源黑体 `Noto Sans SC` + 精致无衬线
  - 正文编辑区字号与行距需明显优于一般 App（长文阅读舒适度是核心竞争力）
- **配色**：暖中性纸感底色 + 墨色正文 + 单一点缀色（避免「白底紫渐变」这类 AI 陈词）
- **背景质感**：极淡的纸纹 / 分层透明，而非纯色平铺
- **图标**：统一 Lucide，禁止 emoji 充当图标
- **动效**：一次编排好的页面载入错落浮现 + 克制的 hover 过渡，不做散碎微交互

> 上述为方向；正式的 Design Contract（含 design tokens、组件规范、App Shell + 导航骨架）在原型阶段按 `rapid-prototype-craft` 规范冻结后再写代码，保证多页一致性。

### 9.3 关键交互

- **流式写作可中断**：正文逐字出现，随时「停止」并保留半成品
- **diff 预览修订**：AI 修订以 diff 形式呈现，用户可逐条接受/拒绝
- **干预开关常驻**：工作台顶部常显当前模式，一键切换
- **成本可见**：每章生成后显示 Token 与费用

## 11. 里程碑

> 不含时间估算，只定义交付物与验收标准。

### P0 · 一致性内核（当前重点）

**形态**：FastAPI 纯后端 + CLI，**不含 UI**。用脚本驱动即可跑通。

**交付物**
- 项目骨架 + OpenAI 兼容适配层（含 Provider 配置、重试、降级、计量）
- 真相文件 schema 与读写（Proposal → Validate → Commit）
- 上下文组装（Token 预算 + BM25 检索 + 关联章节推荐）
- Architect / Writer / Auditor(L1) 三条最小链路
- Auditor(L2) + Reviser 闭环
- step 级 checkpoint 与恢复
- CLI：`novel new / plan / write <n> / audit / resume`

**验收标准（全部满足才算完成）**
1. 一条命令从一句灵感生成 **10 章**正文
2. **伏笔回收率可统计**（埋了 N 条、回收 M 条）
3. **角色状态不漂移**：L1 规则零违规
4. **中断可续**：kill 进程后重启，精确续跑，不重复不丢稿
5. 每章 Token 与成本可查

### P1 · 双模式流水线

- 干预策略层（auto / confirm / manual）
- Coordinator 全局编排 + 滚动视界规划
- 全自动模式端到端跑完整本（含 stop_conditions 熔断）

**验收**：全自动模式能无人值守写完 20 章，且中途可切人工接管。

### P2 · Web 工作台

- 按 Design Contract 实现前端（先复用原型的设计与页面结构）
- 写作工作台、共创对话、角色卡、伏笔看板、设置
- SSE 流式 + diff 修订预览 + 干预开关

**验收**：浏览器内完成「立项 → 逐章确认 → 定稿」全流程。

### P3 · 增强能力

- 拆书（导入已有小说反写设定）
- 文风仿写（`style_profile.json` 生成与注入）
- 提示词工坊（模板管理与复用）
- 去 AI 味的规则扩充

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **范围爆炸**（最大的风险） | 永远发不了版 | P0 严格限定为「后端内核 + CLI」，UI、拆书、工坊全部后置 |
| **Token 成本失控** | 用户流失 | 上下文分层预算 + 预算熔断 + 成本可见 |
| **全自动质量天花板** | 产出不可用 | 审计只做能做的；冲突项标记待人工，不追求 100% 自动 |
| **修订死循环** | 烧钱 | 单章修订上限 2 轮，超限挂起 |
| **模型输出格式不稳** | 流程中断 | JSON 解析容错 + 能力探测降级 + 重试带错误上下文 |
| **长上下文失控** | 成本与质量双降 | 摘要压缩 + 检索取用，不靠「全塞进 prompt」 |
| **厂商锁定** | 议价权与可用性风险 | 只依赖 OpenAI 兼容协议，Provider 可配置可替换 |
| **密钥泄露** | 安全事故 | 密钥仅服务端、日志脱敏、前端永不接触 |
| **跨模型质量不一致** | 换模型后产出崩坏 | 关键环节主备模型能力对齐；换模型后跑回归样本 |
